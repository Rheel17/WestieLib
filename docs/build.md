# Building

Toolchain on this machine: MSYS2 MinGW-w64 GCC (`C:\msys64\mingw64\bin`), plus the CMake and Ninja that ship with
CLion. `cmake-build-debug/` belongs to CLion; build somewhere else (the session scratchpad) from the
command line.

```powershell
$env:PATH = "C:\msys64\mingw64\bin;$env:PATH"
$cmake = "C:\Users\Levi van Rheenen\AppData\Local\Programs\CLion\bin\cmake\win\x64\bin\cmake.exe"
$ninja = "C:\Users\Levi van Rheenen\AppData\Local\Programs\CLion\bin\ninja\win\x64\ninja.exe"
& $cmake -S "D:\C++\WestieLib" -B $build -G Ninja "-DCMAKE_MAKE_PROGRAM=$ninja" -DCMAKE_BUILD_TYPE=Debug
& $cmake --build $build                # --clean-first shows every warning again
```

The result is `$build\WestieLib.exe`: one statically linked executable with no DLL dependencies. The build must stay
free of warnings (`-Wall -Wextra`). Count them with `Select-String ': warning'`; a plain `warning` match also hits
file names such as `Win32Error.cpp`.

## CMake

- Every `.cpp` is listed by hand in `add_executable`; add new ones there. Headers aren't listed.
- Include roots: `src/` (so `#include "ui/framework/Window.h"`), `res/`, and `<build>/generated/`.
- Definitions: `UNICODE _UNICODE STRICT WIN32_LEAN_AND_MEAN NOMINMAX WINVER=0x0A00 _WIN32_WINNT=0x0A00` (Windows 10).
- `-municode` (entry point `wWinMain`), `-static`, WIN32 subsystem.
- Links `comctl32` (TaskDialog and the common controls) and `uxtheme` (the menu bar's drawing). The manifest selects
  ComCtl32 v6, which `TaskDialogIndirect` needs. MinGW's `uxtheme` import library has no `OpenThemeDataForDpi`, so
  the code uses `OpenThemeData` and reopens the theme after a DPI change. `shell32`, `ole32` and `uuid` bring the
  known folders, COM and the folder picker.
- [glaze](https://github.com/stephenberry/glaze) reads and writes JSON. `FetchContent` clones it at a pinned tag
  (`GIT_TAG` in `CMakeLists.txt`) into `<build>/_deps`, so the first configure of a build folder needs the network.
  It's header-only, and `SYSTEM` keeps its headers out of the warnings. To update it, change the tag; its release
  notes list breaking changes.
- `CMAKE_CXX_SCAN_FOR_MODULES OFF`: the project uses headers, not C++20 modules, because windows.h is macro-based.
- `project(VERSION)` feeds `src/Version.h.in` → `<build>/generated/Version.h` (`WESTIELIB_VERSION_*` macros), which
  the resource script uses for `VERSIONINFO`.

## Resources (`res/`)

- `WestieLib.rc` holds the app icon, the glyph icons, the manifest and `VERSIONINFO`. Resource IDs are macros in
  `src/ResourceIds.h`, shared by the `.rc` and C++ (`IDI_APP_ICON`, `IDI_PLUS`, …).
- `res/glyphs/*.ico` are the UI's glyphs, rendered by `res/make-glyphs.ps1` from the icon table in
  `plan/ui-mockup.html`. WPF draws each glyph's SVG markup at 16–48 px (100–300% scaling). Glyphs marked in the
  script's table also get a `-disabled` copy (grayscale at 45% opacity) for disabled toolbar buttons. The files are
  committed. To add a glyph, add its name to the table and run the script, then add an `ICON` line to the `.rc` and
  an `IDI_` macro. CMake globs `res/glyphs` for the `.rc`'s dependencies.
- `make-icon.ps1` and `make-glyphs.ps1` share the ICO writer in `res/IconFile.ps1`.
- `WestieLib.manifest` declares Per-Monitor V2 DPI, ComCtl32 v6 and the Windows 10 `supportedOS`. MSYS2 links its own
  `default-manifest.o` too; ours takes precedence, which `tests/ui/ui-checks.ps1` confirms (DPI awareness 2).
- windres doesn't track the `.ico` and `.manifest`, so `OBJECT_DEPENDS` in CMake does.
- `WestieLib.ico` is generated by `res/make-icon.ps1` from the `app` glyph in `plan/ui-mockup.html`: 16–256 px, DIB
  frames with PNG at 256 px. The `.ico` is committed; rerun the script only to change the icon. .NET's `Icon` class
  can't read PNG frames, so a System.Drawing preview shows the 256 px size upscaled from 64 px. Windows reads it fine.
